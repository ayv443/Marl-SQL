-------------------------------------------------------------
Your pilot (0.5B, 150 steps) proved the pipeline works, but it can't be compared with
DPO and RLOO because almost every setting is different. We looked at your results folder:

  Setting                 Your pilot run                      This run (same as DPO/RLOO)
  ----------------------  ----------------------------------  -----------------------------------
  Code                    old multi-agent plan scripts        branch text2sql-rl, train_rl.py
  Library versions        TRL 1.14, Transformers 5.19,        TRL 0.24, Transformers 4.56,
                          PEFT 0.21                           PEFT 0.17 (requirements.txt)
  Model                   Qwen2.5-Coder-0.5B-Instruct         Qwen2.5-Coder-1.5B-Instruct
                                                              (unless we all switch to 0.5B)
  Training data           train_spider only (7000 -> 6743)    train_spider + train_others
                                                              (8659 -> 7040, 6631 train / 409 val)
  Questions trained on    random subset                       only "mixed" questions from Eby's
                                                              feasibility run (tags.json)
  LoRA                    r=16 on q_proj, v_proj only         r=16, alpha=32 on q,k,v,o,gate,up,down
  Learning rate           1e-5, fell to 0 over the run        5e-5 (still decays over the run, but
                          (about 5e-6 on average)             from a higher start and over more steps)
  Length of run           150 steps, ~0.6 epoch of a subset   600 steps (final number agreed after
                                                              smoke tests), 4 questions x 4 tries
                                                              per step
  KL coefficient (beta)   (TRL default)                       0.04, set explicitly
  Evaluation              200 dev questions                   Eby evaluates everything on the full
                                                              sets, one machine, one script

Why 1616 empty results and not 254 like your run: we also use train_others (1659 questions
from Yelp/IMDB/Academic/... databases) and those databases are mostly empty in Spider.

Things you hit last time that are already handled in this code:
  - chat template: every script uses it (vLLM llm.chat, apply_chat_template, chat-format data)
  - one LoRA adapter per method, no get_peft_model x3
  - query timeout uses sqlite's progress handler (tested: stops at 5.0 s)
  - SQL is read from <answer> tags, a ``` block or plain SQL starting a line, so a correct
    answer without tags is not counted as a crash

Two things you hit that may or may not happen with these versions:
  - the Triton "cuda.h not found" crash in TRL
  - needing float32 loading on the T4
The smoke test (section 9) will show it. If either happens, send Eby the error. Do NOT
patch your copy of the code: any fix has to go into the shared code so DPO and RLOO get
it too.

1. THE SETTINGS (LOCKED VALUES)
-------------------------------------------------------------
These are the same for DPO, GRPO and RLOO. Do not change any of them on your own.

  Model ......................... Qwen/Qwen2.5-Coder-1.5B-Instruct (*)
  LoRA .......................... r=16, alpha=32, dropout 0.05, all attention + MLP layers
                                  (set in common.py, nothing to pass)
  Precision ..................... fp16 (T4 has no bf16), gradient checkpointing on
  Learning rate ................. --lr 5e-5
  KL coefficient beta ........... 0.04 (default in train_rl.py, same for GRPO and RLOO)
  Completions per question ...... 4  (default --num_generations 4)
  Questions per step ............ 4  (default --prompts_per_step 4) = 16 completions per step
  Temperature ................... 0.8 (default)
  Max completion length ......... 256 tokens (common.py)
  Max prompt length ............. 2048 tokens (longer prompts are skipped everywhere)
  Training questions ............ only "mixed" questions from tags.json (default --only_mixed 1)
  Steps ......................... --max_steps 600 (*)  SAME for GRPO and RLOO
  Seed .......................... --seed 0 (seed 1, 2 later only if agreed)
  Checkpoint every .............. 100 steps (default --save_steps 100)
  Reward ........................ +1 correct result, 0 wrong result, -0.1 error/no SQL/timeout

  (*) Fixed on 8 Oct (section 10.3): 1.5B model, max_steps 600 for both GRPO and RLOO.

The run will be called  grpo-1.5b-s0  (or grpo-0.5b-s0). The scripts name it automatically

    The part after wandb.ai/ must be Eby's team (or your own name if you use the

  - Log lines look like:  step 12/50 | 31.2 s/step | loss=..., reward=..., kl=...
  - If you get a Triton "cuda.h" error or an fp16 / "unscale FP16 gradients" error: copy the
    full error and send it to Eby. Don't patch the code.

Get the numbers Eby needs (average seconds per step and peak GPU memory):
      python - <<'EOF'
import json, glob
f = sorted(glob.glob("outputs/grpo-*/logs/*_steps.jsonl"))[-1]
rows = [json.loads(l) for l in open(f)]
rows = [r for r in rows if "reward" in r]   # skip the end-of-training summary line
last = rows[-1]
print("file:", f)
print("steps:", last["step"], "| avg s/step:", last["seconds_per_step"], "| peak GPU GB:", last.get("gpu_mem_peak_gb"))
print("first reward:", rows[0].get("reward"), "| last reward:", last.get("reward"), "| last kl:", last.get("kl"))
EOF

Estimated full run time:  hours = avg_s_per_step x max_steps / 3600
(e.g. 30 s x 600 = 5 hours). Send Eby: s/step, peak GPU GB, instance type, any errors.

13. WATCHING THE RUN
-------------------------------------------------------------
Where to look:

  Log:      tail -f logs_grpo.txt   one line per step like
              step 120/600 | 29.8 s/step | loss=..., reward=..., kl=...
            "checkpoint saved: checkpoint-100" every 100 steps, "FINISHED after ..." at the end.
  W&B:      run grpo-1.5b-s0, every step logged (charts below).
  GPU:      nvidia-smi (one python process using the T4)
  Is it still running?  ps aux | grep train_rl.py | grep -v grep
  Check it every hour or two (start, middle, end).

What normal looks like / what to worry about (W&B names; a few may be missing for RLOO):
  train/reward                         should trend up over hundreds of steps (noisy step
                                       to step, look at the trend)
  train/rewards/valid_sql_reward/mean  share of valid SQL, should go up and stay high
  train/kl                             should rise slowly, not shoot up
  train/completions/mean_length        should stay roughly stable (about 30-45 tokens).
                                       Jumping to 256 = model rambling; dropping to a few
                                       tokens = collapse
  train/frac_reward_zero_std           share of questions where all 4 tries got the same
                                       reward (no learning signal). Climbing toward 1.0 =
                                       plateau
  train/entropy                        a sudden crash toward 0 = exploration stopped
  loss                                 NaN = stop (the log shows "WARNING: loss is NaN")

If several of these go bad at the same time (reward falls, kl explodes, length collapses),
stop the run (kill <PID> from the ps command above) and tell Eby with screenshots. Don't
restart with different settings on your own.

Checkpoints appear every 100 steps in:
      outputs/grpo-1.5b-s0/checkpoint-100, checkpoint-200, ...

14. IF THE RUN STOPS OR FAILS
-------------------------------------------------------------
  The space was stopped / Studio shut it down / the terminal was killed / it crashed
      Checkpoints are saved every 100 steps in outputs/grpo-1.5b-s0/ on the space's disk,
      which survives a stop. Make sure nothing is still running:
        nvidia-smi
        ps aux | grep -E "train_rl.py|EngineCore" | grep -v grep
      then run the SAME command again (12.2). It continues from the last checkpoint: the
      log says "training started at step 300 ..." (or wherever it was). You lose at most
      the steps since the last checkpoint. Each start gets its own log files; keep them all.

  "FAILED ..." with an error at the end of the log
      Send Eby the full error (the last 30-50 lines of logs_grpo.txt). Common ones: section 17.

  Never run two copies at the same time: both would write to the same folder.

      -> something else is using the GPU (a crashed earlier run). Check and stop it:
           nvidia-smi
           ps aux | grep -E "train_rl.py|sample.py|EngineCore" | grep -v grep
           kill <PID>          (kill -9 <PID> if it won't stop)

  FileNotFoundError: tags.json
      -> tags.json isn't in data/processed/ yet: git pull (10.1).

  "wandb: ERROR api_key not configured" / no run in W&B
      -> run "wandb login" (or source ~/SageMaker/.bashrc_t2s), check with
         echo ${WANDB_API_KEY:0:6}, then start the same command again (it resumes).

  Run shows up in your own W&B account instead of Eby's team
      -> "Default team" isn't set (5.1 c). Set it; for a run that's already going, just send
         Eby the link (or move it: run page -> "..." -> Move to the team project).

  Training stopped in the middle
      -> run the same command again, it resumes from the last checkpoint (section 14).

  Can't start the space on ml.g4dn.2xlarge (no capacity)
      -> use ml.g4dn.xlarge (same T4) or try again later.

  git pull: "untracked working tree files would be overwritten"
      -> see 10.1.

  "bash: activate: No such file or directory"
      -> harmless, the environment was already active.

  vLLM "ERROR ... FA version 2 ... compute capability >= 8"
      -> harmless, it uses a different attention backend on the T4.
